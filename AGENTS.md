# Testing and Evaluation Agent Instructions

## 1. Project Purpose

This repository contains the Testing and Evaluation Agent.

The agent uses Microsoft Agent Framework for orchestration and supports the following testing capabilities:

1. Smoke testing
2. Integration and self-testing
3. Evaluation testing
4. Plan-versus-implementation testing
5. UI testing
6. Test-case generation
7. Playwright script generation

Playwright MCP is used for browser exploration, locator discovery, accessibility inspection, screenshots, and test-generation assistance.

Playwright Test with TypeScript is the deterministic and repeatable browser test execution layer.

Azure DevOps MCP integration is reserved for a future version of the project.

## 3. Project Architecture

### 3.1 Python Responsibilities

All Python code belongs under `src/`.

#### `src/agents/`

This directory contains:

- Agent creation
- Agent instructions
- Agent entry points
- Model-client construction
- Skill selection
- Delegation to workflows

#### `src/workflows/`

This directory contains:

- Workflow sequencing
- State transitions
- Approval checkpoints
- Resumable workflow behavior
- Skill orchestration
- Failure-state handling

#### `src/tools/`

This directory contains deterministic operations, including:

- File operations
- Artifact persistence
- Playwright process adapters
- MCP adapters
- Report assembly
- Input validation helpers
- Execution-result parsing

Model reasoning must not replace deterministic operations that can be implemented as normal code.

#### `src/evaluators/`

This directory contains:

- Rubric loading
- Evaluation logic
- Score normalization
- Baseline comparison
- Evidence validation
- Evaluation explanations

#### `src/models/`

This directory contains Pydantic models for:

- Agent requests
- Workflow state
- Test cases
- Test steps
- Approval decisions
- Script-generation requests
- Execution results
- Evaluations
- Reports
- Artifact metadata

### 3.2 TypeScript Responsibilities

All browser-execution code belongs under `tests/`.

#### `tests/generated/`

Contains agent-generated draft Playwright tests.

Files in this directory:

- Are drafts
- Must not run automatically
- Must not be treated as approved
- Must not be promoted without human review

#### `tests/smoke/`

Contains approved smoke tests.

#### `tests/integration/`

Contains approved integration and end-to-end tests.

#### `tests/ui/`

Contains approved tests for:

- Functionality
- Visual behavior
- Responsiveness
- Performance
- Usability
- Accessibility

### 3.3 Test Specification Responsibilities

#### `specs/generated/`

Contains draft test cases generated by the agent.

#### `specs/approved/`

Contains test cases approved by a human reviewer.

A generated specification must never be treated as approved only because generation completed successfully.

## 4. Required Approval Checkpoints

The workflow must enforce all approval checkpoints.

### Checkpoint A: Test-Case Approval

Generated test cases must be reviewed and approved before Playwright scripts are generated.

A rejection must return the workflow to test-case revision.

### Checkpoint B: Playwright Script Approval

Generated Playwright scripts must be reviewed and approved before execution.

A rejection must return the workflow to script revision.

### Checkpoint C: Evaluation Approval

Evaluation results and recommendations must be reviewed before downstream implementation changes are proposed or performed.

### Checkpoint D: External-System Approval

Any future action involving App Factory, Azure DevOps, or another external system requires explicit human approval.

No agent, workflow, tool, or skill may bypass these approval checkpoints.

---

## 5. Execution Safety Rules

All generated code must follow these safety rules:

1. Never execute generated Playwright scripts automatically.
2. Never run tests against a production environment by default.
3. Never perform destructive actions without explicit human approval.
4. Never modify the application being tested.
5. Never commit secrets, passwords, API keys, tokens, certificates, or connection strings.
6. Never store credentials directly inside generated test files.
7. Never silently move generated files into approved directories.
8. Never report that a test passed unless deterministic execution evidence exists.
9. Never report that an implementation matches a plan without traceable comparison evidence.
10. Never hide execution failures, evaluator uncertainty, or missing evidence.
11. Never connect to Azure DevOps MCP unless the integration has been implemented and explicitly enabled.
12. Never perform App Factory changes from this project.
13. Never continue into a dependent workflow step after a blocking failure.
14. Never overwrite an approved artifact with a generated draft.

## 6. Skill Architecture

Every skill must be stored in the following format:

`skills/<skill-name>/SKILL.md`

The initial skill directories are:

- `skills/smoke-testing/`
- `skills/integration-self-testing/`
- `skills/evaluation-testing/`
- `skills/plan-vs-implementation/`
- `skills/ui-testing/`
- `skills/generate-test-cases/`
- `skills/generate-playwright-scripts/`

Each `SKILL.md` file must define:

1. Skill name
2. Purpose
3. Supported inputs
4. Expected outputs
5. Required procedure
6. Guardrails
7. Acceptance criteria
8. Failure behavior
9. Artifact requirements
10. Approval requirements

Skill files contain instructions and domain behavior.

Reusable and deterministic Python logic must remain under `src/tools/`. Python implementation files must not be placed inside skill directories.

## 7. Skill Execution Rules

Before executing a skill, the workflow must:

1. Validate the input against the relevant Pydantic model.
2. Load the complete `SKILL.md` file.
3. Confirm that all required inputs are available.
4. Apply the skill guardrails.
5. Execute only the permitted behavior.
6. Produce structured output.
7. Validate the structured output.
8. Persist artifacts only in the designated generated directory.
9. Record warnings and incomplete information.
10. Request human approval when required.

If required input is missing, the skill must return a structured failure result instead of inventing information.

## 8. Smoke-Testing Rules

The smoke-testing skill validates whether essential solution components are available and operational.

Smoke testing should verify:

- Expected components exist
- Required pages or services load
- Required data can be accessed
- Essential navigation works
- Components are included in the overall solution
- The application can complete its basic intended path

Smoke tests should be:

- Fast
- Independent
- Non-destructive
- Repeatable
- Focused on critical functionality

A smoke-test failure must include:

- Failed component or step
- Expected result
- Actual result
- Available error details
- Evidence references
- Suggested next action

---

## 9. Integration and Self-Testing Rules

Integration testing validates whether connected parts of the solution work together.

Self-testing validates the testing agent's own process.

The skill should determine whether:

- The workflow completed successfully
- Required skills were selected correctly
- Each agent or tool completed its responsibility
- Approval checkpoints were respected
- Expected artifacts were created
- Generated artifacts passed schema validation
- Execution errors occurred
- Errors originated from the application, test, skill, tool, model output, or workflow
- Existing skill instructions were insufficient or ambiguous

Self-testing may recommend improvements to a skill or workflow.

Self-testing must not:

- Silently rewrite a skill
- Automatically activate an updated skill
- Hide failed workflow steps
- Continue past a failed safety checkpoint

Scheduled execution may be added in a future iteration but is not enabled by default.

## 10. Evaluation-Testing Rules

Evaluation testing is used for AI-based features and agent-generated outputs.

Evaluation must be configurable because final standards require alignment with the QA team.

Evaluation assets belong in:

- `evals/datasets/`
- `evals/rubrics/`
- `evals/baselines/`
- `evals/results/`

Each evaluated criterion must include:

- Criterion identifier
- Criterion name
- Criterion description
- Evaluation outcome or score
- Evidence references
- Rationale
- Confidence or uncertainty
- Recommended improvement when appropriate

Do not produce a score without an explanation and supporting evidence.

Evaluation logic must not be tightly coupled to one evaluation provider or SDK. Provider-specific behavior must be implemented through an adapter.

## 11. Plan-Versus-Implementation Rules

The plan-versus-implementation skill acts as an independent reviewer.

The comparison must consider:

1. The original user request
2. The approved implementation plan
3. The generated or modified implementation artifacts
4. Test-execution evidence
5. Evaluation evidence
6. The final observable result

The comparison must classify each requirement as one of the following:

- Fully implemented
- Partially implemented
- Missing
- Changed
- Additional unrequested behavior
- Not verifiable

Each finding must include:

- Requirement reference
- Implementation evidence
- Test evidence when available
- Gap description
- Impact
- Suggested improvement

The reviewer must not automatically change the implementation.

If material drift exists, the workflow must request human review and provide specific recommendations.

## 12. UI-Testing Rules

UI testing covers:

- Functionality
- Visual design
- Responsiveness
- Performance
- Usability
- Accessibility

Playwright MCP may assist with:

- Browser exploration
- Locator discovery
- Screenshot capture
- Accessibility inspection
- Understanding page structure
- Assisting test generation

Playwright Test must be used for repeatable execution.

UI tests must avoid subjective claims without a defined rubric or measurable evidence.

Accessibility testing should prefer semantic roles, accessible names, labels, keyboard behavior, focus behavior, and machine-readable accessibility results.

Visual testing must clearly distinguish between:

- Structural failure
- Functional failure
- Responsive-layout failure
- Visual difference
- Missing baseline
- Rendering instability

## 14. Playwright Script Generation Rules

Generated Playwright scripts must:

1. Use `@playwright/test`.
2. Be written in TypeScript.
3. Map every test to an approved test-case identifier.
4. Use Playwright assertions.
5. Prefer accessible, user-facing locators.
6. Keep tests independent.
7. Reuse fixtures when appropriate.
8. Avoid hard-coded credentials.
9. Avoid arbitrary timeout-based sleeps.
10. Capture useful evidence on failure.
11. Avoid fragile selectors.
12. Avoid performing destructive actions.
13. Follow the repository's Playwright configuration.
14. Be stored only under `tests/generated/`.
15. Remain unexecuted until separately approved and triggered.

Preferred locator order:

1. `getByRole`
2. `getByLabel`
3. `getByPlaceholder`
4. `getByText`
5. `getByTestId`
6. Stable CSS locator when no accessible locator is available
7. XPath only as a last resort

Do not use `page.waitForTimeout()` as a normal synchronization strategy.

Use observable application state, locator assertions, URL assertions, response events, or load-state checks instead.

## 15. Execution Rules

Script generation and script execution are separate operations.

An execution request must include:

- Approved script reference
- Target environment
- Base URL
- Browser
- Headless or headed mode
- Retry policy
- Evidence settings
- Approval reference
- Run identifier

Before execution, verify:

1. The test exists in an approved execution scope.
2. Script approval is present.
3. The target environment is permitted.
4. Production execution is not enabled by default.
5. Required environment variables exist.
6. No destructive behavior is present.
7. The execution command is deterministic.

Execution results must include:

- Run identifier
- Test-case identifier
- Script path
- Start time
- End time
- Status
- Error information
- Screenshot references
- Trace references
- Retry information
- Environment information

## 17. Error Handling

When a workflow step fails:

1. Record the failing workflow step.
2. Record the error type.
3. Preserve available evidence.
4. Classify the likely failure source when possible.
5. Stop dependent unsafe steps.
6. Return a structured failure result.
7. Suggest corrective actions.
8. Mark partial artifacts as incomplete.
9. Preserve the run identifier for traceability.

Do not use broad exception handling that hides the original error.

If an exception is converted into a domain-specific error, preserve the original exception as the cause.

## 18. Python Coding Standards

All Python code must follow these rules:

- Use Python 3.11 or newer.
- Use type hints for all public functions and methods.
- Use Pydantic models at workflow and adapter boundaries.
- Prefer asynchronous interfaces for model and MCP interactions.
- Use `pathlib.Path` for filesystem paths.
- Use structured logging.
- Keep functions focused and testable.
- Separate model reasoning from deterministic operations.
- Avoid global mutable state.
- Avoid circular imports.
- Use dependency injection where practical.
- Validate external input.
- Include meaningful docstrings for public modules, classes, and functions.
- Do not suppress exceptions without recording context.
- Do not hard-code repository paths.
- Do not hard-code model deployment names or credentials.

---

## 19. TypeScript Coding Standards

All TypeScript Playwright code must follow these rules:

- Use strict TypeScript.
- Use Playwright Test fixtures.
- Use Playwright assertions.
- Keep selectors readable.
- Prefer accessible locators.
- Keep tests independent.
- Keep reusable setup in fixtures or helper modules.
- Avoid undeclared dependencies.
- Avoid hard-coded secrets.
- Avoid fixed delays.
- Avoid duplicated test logic.
- Keep each test focused on one clear behavior.
- Include the source test-case identifier in the test title or metadata.

---

## 20. Model Usage Rules

The Microsoft Foundry model may be used for:

- Understanding implementation plans
- Classifying requirements
- Generating draft test cases
- Generating draft Playwright scripts
- Explaining evaluation evidence
- Comparing plans and implementation results
- Producing improvement recommendations

The model must not be treated as deterministic execution evidence.

Model-generated output must be validated before it is persisted or used by another workflow step.

A model response must not directly:

- Execute generated scripts
- Approve generated artifacts
- Modify the tested application
- Perform destructive operations
- Promote drafts into approved directories
- Claim a real-world test result without execution evidence

## 21. MCP Rules

### Playwright MCP

Playwright MCP is intended for:

- Live browser exploration
- Page-structure inspection
- Locator discovery
- Screenshot assistance
- Accessibility inspection
- Script-generation support

Playwright MCP must not bypass the separate Playwright Test execution process.

### Azure DevOps MCP

Azure DevOps MCP is out of scope for the current implementation.

Future integration may support:

- Reading test cases
- Reading test suites
- Mapping repository scripts to ADO cases
- Synchronizing execution results
- Synchronizing evidence references

Do not implement or activate ADO MCP behavior unless the project scope is explicitly updated.

## 23. Testing Requirements for New Code

New deterministic Python code should include unit tests.

Tests should cover:

- Successful behavior
- Input validation
- Missing input
- Invalid state transitions
- Approval-gate enforcement
- File-path safety
- Serialization and deserialization
- Error propagation
- Artifact status changes

Workflow tests must verify that:

- Script generation cannot occur before test-case approval
- Execution cannot occur before script approval
- Evaluation approval is required before downstream proposals
- Failed steps do not incorrectly advance the workflow
- Generated artifacts are written only to generated directories

New code is complete only when:

1. The implementation matches `plan.md`.
2. Public interfaces use appropriate types.
3. Input validation is present.
4. Failure paths are handled.
5. Relevant tests exist.
6. Formatting checks pass.
7. Lint checks pass.
8. Type checks pass.
9. No secret is introduced.
10. Approval gates remain enforced.
11. Generated artifacts are stored in the correct directory.
12. Traceability is preserved.
13. Documentation is updated when behavior changes.
14. Generated code is complete and not truncated.
